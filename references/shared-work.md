# 共享任务与变更流程

## 选择唯一任务源

有共同 GitHub 读写能力时，以业务仓库 Issues 为任务源、PR 为候选交付、`main` 或约定分支为已接受基线。GitHub Projects 只作视图，不复制任务正文。

没有共同远端能力时，使用项目内 `tasks/`；一任务一文件，同一记录追加进展。接入 GitHub 后迁移记录并在旧位置留下跳转说明，停止双写。不要把无法读取或回填的聊天当作持续交付者。

任务状态只在约定任务源维护：待做→可做→执行中→待审／待测→已接受；另有阻塞、取消。执行者追加进展与提交，总监确认分配、接受与取消。关闭不等于已接受，结束原因必须明确。

## 分配与回填

一个总监入口串行分配：确认依赖和可改范围，记录任务修订、基线、当前 `run_id`。运行编号代表一次授权执行，不是 GitHub 用户名。未分配者登记能力／领取申请，等待确认，不匿名抢待做任务。

Issue 头部保存当前约定；评论保存申请、确认、进展、结果与决定。涉及目标／范围／依赖的变化才提高任务修订号，普通进度评论不使任务自动失效。

文字台账不是原子锁，单一派工者也不能制止恶意执行者。若出现多调度者或真正自动抢占需求，先用成熟现成能力补足，再验证重复领取、过期运行和停机恢复，不靠更多提示词声称保证。

## GitHub 原生操作

优先使用当前已有连接器或 CLI，先核对目标仓库与授权，不输出凭据、不自动安装工具。以下仅是明确目标后的操作形状，`OWNER/REPO`、编号及文件路径必须由实际项目替换：

```sh
gh issue list --repo OWNER/REPO --state open
gh issue view 12 --repo OWNER/REPO --comments
gh issue create --repo OWNER/REPO --title '任务标题' --body-file task.md
gh issue comment 12 --repo OWNER/REPO --body-file result.md
gh pr list --repo OWNER/REPO --state open
gh pr view 8 --repo OWNER/REPO
gh pr diff 8 --repo OWNER/REPO
```

不是在不知道授权时执行写操作，也不是要求老板运行命令。任务分支提交、PR 创建和整合由具备相应权限的执行路径完成。没有远端写能力的内部执行者，可把产物交到共同工作区，由获授权整合者提交。

## 变化与暂停

记录变化及理由、影响接口／消费者／数据／测试、哪些任务继续／暂停／重验、决定与生效版本。采纳后更新有效说明及任务修订。保存旧决定的原因，不把旧版本伪装成现状。

仅对相关证据标失效。执行者在开工、恢复、提交前核对；整合者接受前再次核对。无法立即通知或停止时记录未确认，不宣称文件更新已广播到所有聊天。危险动作需实际停止或现实干预。

## 调度边界

共享记录解决异步交接，不自动唤醒模型。现有宿主能委派／通知且已授权就使用；否则允许负责人启动或催办，但不要求其搬运技术报告。

不要默认设置轮询、常驻后台或为每个任务创建独立用户聊天。只有明确要求无人值守，才另选现成调度能力，并确认权限、费用、停止、原子领取和恢复方式。
